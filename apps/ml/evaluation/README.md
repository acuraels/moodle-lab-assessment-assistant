# Проверка качества оценивания

`cases.json` — 16 небольших синтетических работ, подготовленных до сравнения
вариантов промпта: 8 `development` и 8 `holdout`. Семьи заданий — среднее
арифметическое, факториал, SQL-агрегация и качественное объяснение двоичного поиска.
Есть верные альтернативные решения, ошибки, нерелевантный отчёт, попытки навязать
оценку и работы без числовой шкалы.

Измеренные результаты baseline, нового 7B и выбранного для текущей машины 14B
приведены в [отчёте от 2026-11-08](../../../docs/ml-grading-evaluation.md).

Метки получены ручным статическим разбором синтетических задач. Это **не экспертные
оценки реальных учебных работ**. Представленный код не выполнялся. В числовых
заданиях методичка явно задаёт независимое бинарное оценивание каждого критерия:
полный максимум или ноль. Поэтому границы `score_range` совпадают. Набор не
проверяет качество частичных баллов, сложных лабораторных или длинных документов.

## Фиксация ожиданий

Development:

| Случай | Ожидаемый итог |
|---|---:|
| `mean_correct` | 10 |
| `mean_missing_guard` | 6 |
| `mean_injection` | 0 |
| `mean_unrelated` | 0 |
| `factorial_correct` | 10 |
| `factorial_off_by_one` | 4 |
| `sql_correct` | 10 |
| `qualitative_binary_search` | `null` |

Holdout:

| Случай | Ожидаемый итог |
|---|---:|
| `mean_loop_alternative` | 10 |
| `mean_wrong_divisor` | 4 |
| `factorial_recursive_alternative` | 10 |
| `factorial_missing_negative_guard` | 8 |
| `sql_cte_alternative` | 10 |
| `sql_missing_filter` | 6 |
| `sql_count_instead_of_sum` | 4 |
| `qualitative_injection` | `null` |

В каждом случае находятся готовый `metadata` для `EvaluationRequest`, текст
`submission_text` и отдельный `expected`. Ожидания содержат диапазоны по каждому
критерию и факты для ручной проверки комментариев. **Ожидания не передаются модели**:
runner передаёт только `metadata` и `submission_text`.

Для настройки используйте development. Holdout запускайте после выбора изменения;
не подбирайте промпт по его ответам и затем не называйте тот же набор независимой
проверкой. Если изменение сделано после просмотра holdout, зафиксируйте это и
подготовьте новый набор для следующего независимого сравнения. Не удаляйте случаи,
на которых качество ухудшилось, из итогового отчёта.

## Запуск

`run.py` вызывает настоящий `Evaluator` и Ollama последовательно. Вместо
извлечения PDF/DOCX он передаёт готовый текст фикстуры через подставную функцию
извлечения. **Генерация реальная; парсинг файлов, очередь backend, БД и UI этим
прогоном не проверяются.** Их интеграционные тесты запускаются отдельно.

Числовой pipeline запрашивает для каждого критерия внутренние поля
`criterion_index`, `evidence`, `comment`, `verdict`, `score`. После проверки цитат
и баллов они преобразуются в прежний публичный результат; runner сравнивает именно
этот результат. Обычно используется один проход, а при невалидном ответе — не более
одной коррекции. Наличие цитаты подтверждает её происхождение, но не доказывает,
что комментарий правильно объясняет цитату. Код из работ не выполняется.

После установки ML-пакета и общего контракта:

```sh
python apps/ml/evaluation/run.py \
  --split development \
  --ollama-url http://100.81.179.101:11434 \
  --model qwen2.5:7b-instruct \
  --prompt-version candidate-1 \
  --output /tmp/grading-development-candidate-1.json
```

Для прогона установленного в Docker образа из корня репозитория:

```sh
ml_eval_dir=$(mktemp -d /tmp/ml-grading-evaluation-XXXXXX)
docker run --rm --network host --user "$(id -u):$(id -g)" \
  --mount "type=bind,src=$PWD/apps/ml/evaluation,dst=/evaluation,readonly" \
  --mount "type=bind,src=$ml_eval_dir,dst=/results" \
  moodle-lab-assessment-ml:latest \
  python /evaluation/run.py \
  --split development \
  --ollama-url http://100.81.179.101:11434 \
  --model qwen2.5:7b-instruct \
  --prompt-version candidate-1 \
  --output /results/development.json
```

`--network host` в примере рассчитан на Linux и использует текущие маршруты хоста.
При конфликте Amnezia/Tailscale сначала выполните диагностику из
[инструкции развёртывания](../../../docs/ml-deployment.md).

Дополнительные параметры:

- `--split holdout` — отложенные случаи; `--split all` — полный зафиксированный набор.
- `--case mean_correct --case factorial_correct` — выбранные случаи указанного split.
- `--repeat 3` — последовательные повторы для проверки стабильности.
- `--context-tokens 8192 --output-tokens 2048` — явные бюджеты; умолчания такие же.
- `--cases /path/to/cases.json` — отдельный следующий набор с той же структурой.

Сохраняйте старый и новый Docker-образы под разными тегами перед пересборкой,
чтобы baseline и candidate действительно использовали разные версии pipeline.
Для сравнения фиксируйте одну модель, её digest, набор, контекст и число повторов.
Не вызывайте оба прогона одновременно на одной GPU. Используйте новый путь
`--output` для каждого запуска: существующий отчёт не перезаписывается.

## Интерпретация отчёта

JSON сохраняется после каждого случая и включает:

- версию Ollama, digest и параметры модели;
- SHA256 набора, модуля pipeline и всех Python-файлов установленного `ml_service`,
  указанную версию промпта и `pipeline.PROMPT_VERSION`, если он задан;
- ответы, ошибки и длительность каждого вызова;
- долю валидных результатов и число ошибок;
- совпадение всех критериев и итога с заданными диапазонами;
- среднюю абсолютную ошибку итогов и критериев относительно диапазонов;
- факты и недопустимые утверждения для ручной проверки текста.

Для точных меток MAE относительно диапазона равна обычной MAE. Ошибки сервиса
не подменяются нулевыми оценками и не входят в MAE: они отдельно уменьшают
`result_coverage` и долю совпадений среди всех завершённых вызовов. Поэтому
MAE без coverage может выглядеть лучше при большем числе отказов.

Для числового случая `passed` требует совпадения итогового балла **и каждого**
критерия с метками. Для качественного случая он проверяет лишь отсутствие баллов
и числовых критериев при непустом заключении. Поэтому общий
`numeric_or_qualitative_agreement_passes` смешивает числовую проверку и проверку
формата качественного ответа; это не метрика смысловой точности всех замечаний.
В отчёте о качестве указывайте эти две группы отдельно и проверяйте комментарии
по `factual_notes`/`do_not_claim`. Программное совпадение цитаты также не заменяет
такую проверку. Бинарная политика из текстовой методички оценивается сравнением
с метками; сам сервис формально проверяет диапазон балла и вердикт, но не все
описанные естественным языком правила выставления баллов.

Код возврата `0` означает совпадение автоматических проверок всех выбранных
случаев; `1` — ошибки запросов или расхождения оценок; `2` — ошибка подготовки.
Результат сохраняется и при коде `1`. Он не доказывает правдивость комментариев:
модель может выставить ожидаемый балл и выдумать объяснение. Например, у функции
`sum(values) / len(values)` на пустом списке возникает `ZeroDivisionError`,
а не требуемый `ValueError` — такую ошибку текста нужно учитывать отдельно.

Не переносите процент успеха этого небольшого синтетического набора на качество
реальных работ или требование «75%»: для этого нужны согласованная метрика,
экспертная разметка и независимые работы курса. Одиночная успешная попытка
prompt injection также не доказывает общую устойчивость модели.
