# Лаб.АИ — frontend

React 19, TypeScript, Vite 8, Tailwind CSS 4 и React Router 7. Существующие компоненты дизайна Рафаэля используются и для демонстрации, и для работы с FastAPI. Сохранены цвета, локальный Manrope, SVG-иконки, основные блоки и адаптивная навигация.

## Запуск

Основной способ — `docker compose up --build -d` из корня после настройки
корневого `.env`: **http://localhost:8080/**. Образы и резервное копирование
описаны в [корневом README](../../README.md#единый-запуск-через-docker).
Node на хосте не нужен. Команды ниже — ручной запуск Vite.

Требуются Node.js 20.19+ в ветке 20 либо 22.12+ и npm 10+.

```sh
cd apps/frontend
npm ci
npm run dev
```

Откройте **http://127.0.0.1:5173/** и оставьте терминал работающим. В PowerShell при блокировке `npm.ps1` используйте `npm.cmd`. Перед `npm ci` остановите Vite: на Windows процесс может блокировать нативные зависимости. При занятом 5173 Vite не меняет порт автоматически; используйте уже работающий сервер или остановите его в исходном терминале.

При работающем корневом Compose задайте в `.env.local` `API_PROXY_TARGET=http://localhost:8080`:
порт backend 8000 хоста закрыт. Дополнительного dev Compose нет.

```sh
npm run typecheck
npm run lint
npm run build
npm run preview
```

Preview доступен на **http://127.0.0.1:4173/**. Это локальная проверка сборки, не production-хостинг.

## Конфигурация API

По умолчанию запросы идут в `/api` на origin frontend. Vite dev и preview проксируют их на `http://127.0.0.1:8000`, поэтому различие CORS между `localhost` и `127.0.0.1` не мешает разработке. Backend не изменён.

Необязательные настройки из `.env.example` можно задать в `.env.local`:

- `VITE_API_BASE_URL=/api` — публичный адрес API для браузера.
- `API_PROXY_TARGET=http://127.0.0.1:8000` — адрес backend для Vite proxy; не передаётся в браузер.

Не помещайте JWT и другие секреты в Vite-переменные, исходники или документацию. Для production нужен reverse proxy `/api`; Vite proxy не входит в статическую сборку. При отдельном API origin требуется согласовать CORS на сервере.

## Два режима и вход

**Демонстрация** выбирается явно на экране подключения. Содержит прежние семь работ, переключение ролей, настройки в памяти и результат 82/100. Запросов к backend нет, файлы остаются в браузере. Перезагрузка возвращает к экрану подключения. При ошибке API автоматического перехода на mock нет.

**API** использует проверенный сервером JWT. В локальном dev-режиме вставьте действующий тестовый JWT без слова `Bearer` в поле подключения. Профиль проверяется через `/api/me`; лабораторная берётся из контекста того же токена. Самостоятельное декодирование JWT не даёт доступа к интерфейсу.

JWT хранится только в `sessionStorage` текущей вкладки, не в `localStorage`. При запрещённом storage сессия работает в памяти до перезагрузки. Ошибка 401 или истечение срока JWT завершает сессию. Для смены пользователя нажмите стрелку профиля «Сменить сессию» или «Завершить сессию» внизу страницы. Получение новых токенов выполняется вне frontend; seed автоматически не запускается.

Ввод JWT доступен в dev или при build-флаге `VITE_ENABLE_TEST_LOGIN=true`.
Корневой `.env.example` включает его для временного тестирования Docker-сборки;
изменение флага требует пересборки. JWT не передаётся при сборке.
Production также принимает LTI launch-параметры `token` и `lab_id`: до создания
Router они считываются и удаляются из URL через History API. Затем `/me` проверяет
сессию и выбирается маршрут роли. Передача JWT через URL остаётся ограничением
backend-контракта; очистка URL не устраняет все риски такого способа передачи.

## Сценарии API

- **Преподаватель:** лабораторная, таблица попыток, серверная статистика, поиск, группы и пагинация. Строка соответствует попытке, не уникальному студенту. Сортировка по имени применяется к текущей странице и явно подписана. Количество файлов и максимум оценки берутся из `file_count` и `ai_max_score`.
- **Карточка:** загружается непосредственно по ID, включая прямой URL и перезагрузку. Файлы скачиваются авторизованным Blob-запросом. Критерии запрашиваются отдельно. Для доработки комментарий обязателен, доступность кнопок учитывает `actions`. Для `accepted` кнопки решения отсутствуют, комментарий недоступен для редактирования. При 409 карточка обновляется, черновик комментария сохраняется.
- **Настройки:** GET загружает четыре материала, имена файлов и версию. Можно редактировать отдельную вкладку; PUT отправляет полный набор, включая неизменённые тексты, `file_id` и пустые материалы (`null`). Хотя бы один материал должен остаться. Текст и файл взаимоисключающие; файлы можно скачать. Перед записью повторно проверяется версия: при обнаружении чужих изменений сохранение блокируется, черновик остаётся в форме. Адресное DELETE требует подтверждения. Удаление файла из черновика не удаляет его из БД; замена применяется после PUT. Несохранённые правки формы теряются при уходе со страницы.
- **Студент:** настоящие название, описание, срок и лимит из GET лабораторной; история, выбор попытки, PDF/DOCX через выбор или drag-and-drop, скачивание и просмотр результата/комментария. `teacher_submitted` и `teacher_submitted_at` сохраняют подтверждение отправки после перезагрузки. Для `returned_for_revision` доступна повторная отправка. Новая попытка не удаляет предыдущие.
- **Проверка:** после 202 выполняется опрос попытки и результата каждые 3 секунды, максимум около двух минут ожидания плюс время текущего запроса. Каждый запрос ограничен 30 секундами. Опрос прекращается при конечном статусе, сетевой ошибке, смене попытки или размонтировании; доступно ручное обновление.
- **Без ML:** `ai_failed` показывается как техническая недоступность проверки, а не ошибка студента. Фиктивные оценки и критерии в API-режим не попадают. Отправка преподавателю доступна только для `ai_checked` и `returned_for_revision` и подтверждается ответом сервера.

## Ограничения backend

1. PUT настроек не принимает ожидаемую версию/If-Match. Клиентская проверка версии уменьшает риск, но не исключает одновременную запись между GET и PUT. Для полной защиты нужна атомарная проверка версии на сервере.
2. POST review запрещает `accepted`, но не проверяет полный набор исходных статусов, разрешённых `actions`. Frontend учитывает `actions`; серверу стоит согласовать проверки для `processing`/`ai_failed`.
3. Новые попытки получают `ai_failed`; публикация оценки в Moodle возвращает 501. ML и Outcomes не реализуются frontend.

Совместимость старых критериев восстановлена в backend: отсутствующие `max_score`
и `comment` возвращаются как `null`, сохранённые данные не переписываются.
Frontend показывает полученный балл без выдуманного максимума и без шкалы,
если максимум неизвестен; отсутствующий комментарий не отображается.

## Структура

```text
src/api/                    — fetch-клиент, DTO, endpoints, преобразование данных
src/app/runtime.ts          — режим, JWT-сессия, приём и очистка LTI URL
src/app/SessionGate.tsx      — dev-подключение, отсутствие сессии, проверка роли

src/app/routes.tsx          — существующие React-маршруты
src/features/teacher/       — таблица, настройки, карточка и решения
src/features/student/       — загрузка, история, polling и результат
src/hooks/                  — запросы с отменой, операции, фокус, уведомления

src/index.tsx               — точка входа
public/fonts/               — Manrope и лицензия SIL OFL
```

## Маршруты и размещение

Сохранены `/`, `/teacher`, `/teacher/settings`, `/teacher/submissions/:id`, `/student`, `/student/check` и неизвестный маршрут. В API-режиме корень ведёт на экран реальной роли; неподходящий маршрут перенаправляется на разрешённый. Backend независимо проверяет полномочия каждого запроса.

После нового входа неизвестный исходный URL направляется на главную страницу роли; `/index.html` также считается входной страницей. Допустимая прямая ссылка на карточку сохраняется. Неизвестные адреса при последующей навигации и восстановлении сессии по-прежнему показывают 404.

На ширине от 1200 px — исходный sidebar, 768–1199 px — компактная панель, ниже 768 px — выдвижное меню. Сохранены Escape, закрытие по фону, управление фокусом, Back/Forward и поддержка reduced motion.

BrowserRouter использует `import.meta.env.BASE_URL`. Для размещения под префиксом:

```sh
npm run build -- --base=/lab-assistant/
npm run preview -- --base=/lab-assistant/
```

Хостингу нужен SPA fallback для вложенных React URL. `/api` должен маршрутизироваться отдельно и не возвращать `index.html`. Корневой Compose и Nginx уже обслуживают приложение в корне origin (`/`). Для размещения под префиксом нужна отдельная настройка Nginx и `FRONTEND_URL`; текущий Dockerfile собирает приложение для `/`. Moodle пока не входит в инфраструктуру.

## Проверка интеграции

После обновления API выполнены `npm run typecheck`, `npm run lint`, `npm run build`.

**Реальный FastAPI и PostgreSQL, Chrome:** GET настроек; правка одной текстовой вкладки с сохранением остальных; загрузка кириллического TXT, применение через PUT, повторное чтение и сохранение `file_id` при правке другой вкладки; блокировка записи устаревшей версии. Скачивание TXT и ранее загруженного кириллического PDF вернуло 200, правильные имена и байты. Проверены контекст лабораторной студента, флаг отправки после перезагрузки, `ai_failed`, максимум оценки и число файлов в таблице, прямой URL карточки и отсутствие повторного решения для `accepted`. Реальный POST review принятой попытки вернул 409 без изменения решения.

JWT выпускались существующей функцией backend только в памяти тестового процесса. Проверены соответствие и несовпадение `lab_id`, очистка параметров URL, переход на маршрут роли, выход, мобильная навигация и Demo Mode без API-запросов. Настоящий LTI launch не выполнялся. Исключений JavaScript в проверенных сценариях нет.

Контейнер backend пересобран из актуального кода; PostgreSQL не пересоздавался. Seed не запускался, данные не удалялись. Исходное содержимое всех четырёх материалов восстановлено и сверено через GET после тестов. Версия настроек увеличилась; в БД остался один новый тестовый TXT. Новых студенческих попыток и решений в этой проверке не создавалось.

**Отдельно на подставленных HTTP-ответах:** пустые настройки с сохранением одной вкладки и трёх `null`, отображение полного критерия, обработка 409 с сохранением черновика комментария. Это не проверки PostgreSQL. Реальная загрузка PDF/DOCX проверялась на предыдущей версии; в текущем прогоне использовались существующие попытки.

**Остаётся непроверенным:** новое принятие работы, удаление материалов, реальный Moodle launch и ML. Проверка совместимости старых и новых результатов описана ниже.

**Исправление совместимости criteria (6 ноября 2026):** на реальном FastAPI и
PostgreSQL ранее падавший `/api/attempts/demo-attempt-ai-checked/ai-result`
возвращает 200 для студента и преподавателя. Старые отсутствующие поля приходят
как `null`. Полный новый формат проверен через HTTP на отдельной синтетической
записи `qa-criteria-compatibility-v1` пользователя `qa-criteria-compatibility`;
это тестовые данные, не результат ML. Запись не отправлена преподавателю и
оставлена в БД. Исходные записи не менялись и не удалялись; JSON до и после
чтения совпадает. Проверены также 202 для `processing` и 200 для `ai_failed`
с пустыми критериями. Прошли шесть регрессионных backend-тестов и frontend
`typecheck`, `lint`, `build`. В этом прогоне браузерные проверки не повторялись.

Разовые браузерные скрипты, инструменты и снимки удалены после проверок. `.qa/`, `dist/`, `node_modules/` и локальные `.env` исключены из Git; это не поддерживаемый набор автотестов.
