# Backend

FastAPI, SQLAlchemy, Alembic и PostgreSQL 17. Контракты — в [api.md](../../api.md).
Основной запуск и backup описаны в [корневом README](../../README.md#единый-запуск-через-docker).

## Запуск

Настройте корневой `.env` на основе корневого `.env.example`, сохранив фактические
секреты и параметры существующей БД. Из корня:

```sh
docker compose config --quiet
docker compose up --build -d
docker compose ps
```

Проверка через Nginx: **http://localhost:8080/health**. Порты 8000 и 5432 хоста
закрыты; внутри Docker БД доступна как `postgres:5432`. Вложенный Compose заменяется
корневым. `apps/backend/.env` можно сохранить для ручного запуска Python;
корневой Compose его не читает и передаёт настройки контейнеру явно.

## Данные и миграции

Используется внешний volume `backend_postgres_data`. Отсутствие volume — ошибка,
а не повод создать пустую БД. Перед переключением обязателен проверенный backup.
Два PostgreSQL не должны одновременно использовать этот volume. Файлы хранятся
в PostgreSQL как BYTEA и входят в `pg_dump`.

После готовности БД backend выполняет `alembic upgrade head`, затем `exec uvicorn`.
При ошибке Alembic сервер не стартует. Healthcheck использует установленный Python
и проверяет `/health` плюс `SELECT 1`.

```sh
docker compose exec backend alembic current
docker compose logs --tail 100 backend
docker compose restart backend
```

Не запускайте seed для проверки: он меняет существующие демонстрационные данные.
Обычный `docker compose down` сохраняет внешний volume.

## Reverse proxy и LTI

Nginx сохраняет внешний Host с портом, схему, путь и POST body `/lti/launch`.
`FRONTEND_URL` — внешний URL Nginx, например `http://localhost:8080/`.
Uvicorn доверяет proxy headers при условии закрытых Docker-сетей и отсутствия
публикации его порта. Другой reverse proxy потребует пересмотра доверия и схемы.
Для same-origin API CORS не требуется. Moodle и удалённый ML работают отдельно;
Outcomes не подключён.

## Удалённая ML-проверка

Backend обращается к ML-сервису Windows через Tailscale; Ollama вызывается самим
ML-сервисом. Пример: `ML_URL=http://100.81.179.101:8001`. Этот адрес не подтверждает
доступность сервиса: проверяйте соединение из backend-контейнера. `ML_TOKEN` должен
совпадать с `ML_TOKEN` на ML-сервере, если защита токеном включена. Не помещайте
его в Git. При пустом `ML_URL` новые попытки завершаются `ML_NOT_CONFIGURED`.

Приложение запускает один последовательный consumer в lifespan; используйте
один процесс Uvicorn (без `--workers` и без нескольких реплик backend).
Источником заданий служит существующая таблица `attempts`. HTTP-запрос загрузки
возвращает 202 сразу после сохранения; длительная генерация выполняется отдельно.
Backend передаёт только файл попытки, контекст её лабораторной и материалы из
неизменяемого снимка. Транзакция БД не удерживается во время HTTP-запроса.

Миграция `0003_ml_processing` добавляет снимок материалов, техническую причину
ошибки и поля восстановления. Уже сохранённые результаты сохраняются. Старые
незавершённые попытки без снимка завершаются `INVALID_SNAPSHOT`: текущие настройки
преподавателя нельзя выдавать за настройки на момент старой загрузки.

По умолчанию один HTTP-вызов ограничен 540 секундами, всего разрешены два вызова,
задержка повтора — 10 секунд, срок с момента загрузки — 1800 секунд. Повторяются
только временные ошибки. Если backend остановился, незавершённая попытка снова
доступна после истечения сохранённой аренды (тайм-аут HTTP + 5 секунд). Номер вызова
и условная запись защищают результат от запоздалого ответа. `accepted` и другие
завершённые статусы worker не меняет. `ai_failed` по-прежнему учитывается в лимите
попыток; отдельного публичного API повторной проверки пока нет.

`GET /api/attempts/{id}/ai-result` дополнительно возвращает `error: {code,message}`
при технической ошибке. Сообщения безопасны для интерфейса; содержимое документов,
промпты, токены и произвольные удалённые traceback не журналируются.

## Ручная установка и тесты

Из корня репозитория в отдельном Python 3.12 окружении:

```sh
python -m pip install ./packages/assessment-contract
python -m pip install -e './apps/backend[test]'
cd apps/backend
python -m pytest -q tests
```

Тесты ML-интеграции создают отдельную временную SQLite и используют HTTP-заглушки;
они не подключаются к PostgreSQL проекта и не подтверждают реальный inference.
Для проверки production-диалекта и миграции требуется отдельная тестовая
PostgreSQL. На действующей БД миграцию применяют при согласованном развёртывании
после backup. Полный сетевой тест требует доступного Windows ML-сервера.

## Совместимость сохранённых критериев

В ответе `GET /api/attempts/{attempt_id}/ai-result` критерий всегда содержит
`name`, `score`, `max_score`, `comment`. Если максимум или комментарий не были
сохранены в старом JSON, схема ответа возвращает `null`. Максимум не выводится
из общей оценки. Чтение не обновляет PostgreSQL; миграция и повторный seed
для этого исправления не нужны.

Регрессионные тесты схемы запускаются из `apps/backend` в окружении с
установленными зависимостями backend; отдельная установка pytest не требуется:

```sh
python -m unittest discover -s tests -v
```

Тесты не включены в production-образ. Их можно передать через stdin без копирования
в образ (PowerShell, из корня):

```powershell
$OutputEncoding = [System.Text.UTF8Encoding]::new($false)
Get-Content -Raw -Encoding UTF8 apps/backend/tests/test_criteria_compatibility.py | docker compose exec -T backend python - -v
```
